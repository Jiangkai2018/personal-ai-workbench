# ADR-0002：承诺类动作必须经确认中心（提案门）

- 状态：已接受
- 日期：2026-08-21
- 关联代码：`server/src/api/routes/proposals.ts`

## 背景

系统的核心价值主张是"少承诺、重执行"。漏斗里有两类"升格"动作：

1. 想法 → 机会（开始认真评估）
2. 机会 → 目标（承诺投入方向）

它们共同的问题是：**一旦发生就消耗注意力**。直接允许一键升格，会让漏斗形同虚设 —— 用户在记录的兴奋劲儿里顺手点一下，承诺就多了一个。

未来还会有 AI Agent 自动评估、自动建议转正。如果 Agent 能直接改数据，"承诺"就从用户手里转移到了模型手里。

## 决策

**所有承诺类动作（升格/降格承诺状态）一律不直接生效，而是生成"提案"（proposal），由人在确认中心批准后才执行文件操作。**

- 提案记录：动作类型、源实体、摘要、状态（pending / approved / rejected）、决策人与时间
- 批准 = 服务端执行对应文件操作（如想法标记 promoted_to_id + 创建机会）
- 驳回 = 提案留档，源数据不动
- 重复提案返回 409（防 Agent 重复刷提案）
- 首页 Dock 常驻「确认」入口 + 待审角标

## 理由

1. **摩擦即价值**：确认中心把"承诺"从顺手动作变成显式决策，漏斗的筛选作用才成立
2. **Agent 安全边界**：未来任何自动化（评分建议、复盘 Agent）只能走到"提案"这一步，人类保留对承诺的唯一决定权
3. **审计留痕**：谁在什么时候批准/驳回了什么，天然有记录

## 后果

- 转正流程多一步操作（点提案 → 确认页 → 批准）—— 这是刻意的
- 提案本身也是一种实体文件（`data/proposals/`），遵循 ADR-0001
- 新增承诺类动作时的检查项：**必须先有对应 proposal action，不允许直改**

## 备选方案

- **直接升格 + 撤销**：操作更少，但"先承诺再反悔"和"想清楚再承诺"是两种完全不同的心理账户，且撤销并不能收回已付出的注意力
- **二次确认弹窗**：看似有摩擦，实际用户会肌肉记忆式点掉；且无法承载"审计 + Agent 边界"两个诉求
