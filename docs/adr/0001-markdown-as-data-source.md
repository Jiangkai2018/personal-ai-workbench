# ADR-0001：Markdown 文件即数据源

- 状态：已接受
- 日期：2026-08-20
- 关联代码：`server/src/storage/repo.ts`、`server/src/storage/reviewStore.ts`、`server/src/storage/userStore.ts`

## 背景

个人工作台需要持久化想法、机会、目标、任务、提案、复盘等实体。常见做法是 SQLite 或 JSON 文件库（lowdb 之类）。但这个系统的用户是**一个人 + 他的家庭**，数据规模在千级条目以内，且数据本身有很强的"个人笔记"属性。

## 决策

**不引入数据库。每个实体 = 一个带 YAML frontmatter 的 `.md` 文件**，直接存在 `data/` 目录：

```
data/ideas/20260822-idea-1a2b3c.md
---
id: 20260822-idea-1a2b3c
type: idea
scope: personal
track: growth
status: inbox
created_at: '2026-08-22T09:00:00.000Z'
---
想试试把复盘结论沉淀成知识库
```

- 读 = `readdir` + `gray-matter` 逐文件解析；写 = 整文件覆写
- 文件名即 ID：`<日期>-<类型>-<随机后缀>`
- 无索引、无缓存：每次请求都直接读磁盘

## 理由

1. **数据可直读**：打开文件夹就能像看笔记一样看数据，用户对"我的数据长什么样"有完整掌控感
2. **git 即版本控制**：Markdown 的 diff 天然可读，误操作可从历史恢复，未来"自动 git 同步"零成本接入
3. **零迁移**：没有 schema 演化问题 —— 加字段就是 frontmatter 多一行，旧文件缺字段用默认值兜底
4. **可移植**：换电脑 = 拷目录；换工具 = 数据仍是通用格式

## 后果

**接受的代价**

- 读性能 O(文件数)：千级条目、机械盘上最坏也就几十毫秒，个人规模可接受
- 无事务：写一半断电可能损坏单文件 —— 用 git 兜底恢复
- 复杂查询要全量遍历 + 内存过滤：同样受规模保护

**带来的约束**

- 后续所有新实体类型必须走 `EntityStore`，不允许绕过直写文件
- 列表类需求（如复盘时间线）若未来超出文件遍历能力，再讨论索引方案（届时以新 ADR 推翻本决策）

## 备选方案

- **SQLite**：查询强、事务全，但数据变成二进制，"可直读 / git 友好"两大优势尽失
- **lowdb（单 JSON 文件）**：实现更简单，但单文件大了以后整文件重写风险高、diff 不可读
